● THE OSSim ARCHITECTURAL FOUNDATION

What Makes OSSim Different?

Unlike traditional abstract lecture slides or black-box OS visualizers, OSSim unites three core pedagogical pillars into an integrated, zero-install systems laboratory:

🔬 PILLAR 1

Hardware-to-OS Observability

Direct, cycle-stepped architectural inspection of simulated silicon registers (PC, SP, FLAGS, R0–R3), MMU multi-level page tables, TLB hits and misses, system bus contention, and hardware peripheral I/O controllers operating synchronously alongside kernel data structures and process lifecycles.

⚡ PILLAR 2

Algorithmic Experimentation

Interactive, side-by-side comparative solvers across 19 benchmark algorithms—covering CPU scheduling (6 heuristics), contiguous memory allocation (3 fit strategies), virtual memory page replacement (4 policies), secondary storage disk arm movement (6 schedulers), and deadlock avoidance with millisecond Gantt charts, live metrics, and formal analytical report export.

🏗️ PILLAR 3

Progressive Systems Construction

A structured educational continuum guiding learners from isolated algorithmic experiments in The Workshop to full-stack systems engineering in OS Builder Quest and The Capstone Studio—evolving from bare-metal bootstrap and device drivers into a multi-tasking desktop operating system running authentic user applications.

The Three Progressive Levels of Simulation

To prevent conceptual confusion, OSSim explicitly distinguishes three distinct depths of systems representation across its environments:

LEVEL 1

The Classroom • The Workshop • The Test Centre

High-level interactive analogies, theoretical state-machine transitions, step-by-step boot phase animations, and 19 comparative algorithm solvers evaluated against analytical reference solutions with Gantt charts.

LEVEL 2

Subsystem & OS Mechanics Simulation

The Playground • Capstone Playground

Live white-box architectural simulation: cycle-stepped simulated silicon registers (PC, SP, FLAGS, R0–R3), MMU multi-level page tables with dirty-bit tracking, TLB hits/misses, dual-storage HDD cylinder seeks vs NVMe SSD wear-leveling, and dual-mode CPU ring switches.

Authentic low-level systems engineering: students write and synthesize C kernel modules, interrupt vector tables, and device drivers, generating hardware abstraction layer (HAL) code tailored for x86 VGA and RISC-V UART target architectures. All code synthesis and architectural execution are modeled within the browser simulation engine, without executing on actual physical host or target hardware.

● Parallel Architectural Privilege & Trap Mappings (x86 vs. RISC-V)
Architectural Concept x86 Architecture Model RISC-V Architecture Model (RV64)
User Privilege Level CPL 3 (Ring 3 User Mode) U-mode (User Mode)
Kernel Privilege Level CPL 0 (Ring 0 Kernel Mode) S-mode (Supervisor OS); M-mode (machine-mode firmware or machine-mode-only implementation)
System Call Entry INT 0x80 (transfers via IDT gate) or SYSCALL (transfers via MSR IA32_LSTAR) ECALL (traps to handler; delegated to S-mode via medeleg)
Page-Table Control Register CR3 (Paging-structure root pointer: PDBR in 32-bit / PML4 in 64-bit) satp (Supervisor Address Translation & Protection root)
Privilege Return IRET / IRETQ (restores frame from stack) or SYSRET (restores RIP from RCX, RFLAGS from R11) SRET (restores sstatus.SPP & sepc) or MRET (Machine Return)
● THREE EXECUTION JOURNEYS

Three Distinct Hardware/Kernel Pipelines

Rather than treating all system interactions as one generic pipeline, The Playground and Capstone Playground explicitly model three distinct architectural journeys:

8 STAGES • INTERACTIVE INPUT

Keyboard & Display Pipeline

The Playground • Live Interaction
IRQ 1 → Mode Switch → ISR Port 0x60 → TTY Buffer → Sched Wakeup → App Buffer → MMU Dirty → VRAM Blit

Illustrates how simulated hardware interrupts wake a sleeping process, traverse kernel character queues, modify virtual memory frames, and blit glyphs to video memory.

7 STAGES • PERSISTENCE

Storage Persistence Pipeline

The Playground • Save Document
Shell Save → sys_save → VFS Inode → Page Cache Flush → Driver Queue → DMA Transfer → Ack

Demonstrates the synchronous filesystem persistence path: identifying dirty memory buffer frames, queueing disk block requests, executing bus-master DMA transfers, and confirming simulated I/O completion.

8 STAGES • INCEPTION & LAUNCH

Process Inception Pipeline

Capstone Playground • App Launch
Shell Click → Syscall Trap → ELF Load → MMU CR3/satp → PCB Ready → Dispatch → Return → Framebuffer

Traces authentic process creation from desktop click, executable segment mapping, and PCB queue admission to scheduler dispatch and dual-mode user-space return.
